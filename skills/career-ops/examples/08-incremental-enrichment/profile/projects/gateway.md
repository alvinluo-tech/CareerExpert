# 项目卡:统一网关性能重构

- 时间:2024.03 ~ 2024.09
- 角色:技术负责人(2 名协作开发)
- 技术栈:Go、FastHTTP、etcd、Redis、Prometheus
- 一句话简介:替换老旧 Spring Cloud Gateway 接入层,统一鉴权/限流/灰度能力,服务公司全部对外流量
- 代码仓库/项目路径:
  - 个人开源参考/脱敏核心实现: `https://github.com/liang-demo/fast-gateway-core`
  - 本地工作目录: `E:/code/fast-gateway`
  - 归属与真实性: 核心通信与动态配置加载模块全部由本人编写，支持现场 Whiteboard 撕底层设计与代码审查。

## 量化结果(简历可用,有出处)
- P99 延迟 45ms → 18ms(压测报告 #PT-2024-09 + 线上 Grafana)
- 单集群 QPS 3.2 万 → 8.5 万(全链路压测)
- 新服务接入成本从约 3 人日降到 0.5 人日(配置化接入)

## 简历级 bullet
- 主导统一网关重构,替换旧接入层,P99 延迟下降 60%(45ms→18ms),单集群 QPS 提升 165%
- 设计动态配置热加载体系(etcd 分片 watch + 批量合并推送),配置变更生效时间从分钟级降到秒级
- 建立插件化架构,新增接入方平均成本从 3 人日降至 0.5 人日,支撑接入方 12→40+ 的增长

## 可讲细节(面试深挖弹药,不上简历)
- 最难的决策:热加载一致性最终采用"版本号 + 双缓冲 + 可回滚",牺牲强一致换发布效率
- 踩坑:etcd watch 风暴(40+ 服务各自 watch 全量前缀)→ 分片 + 合并推送
- 压测方法论:影子流量 + 生产等比数据集,先在 1/10 集群验证
- 如果重来:会更早引入熔断插件,重构期间出现过一次下游慢导致的雪崩
