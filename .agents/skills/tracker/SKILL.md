# 申请追踪

## 每次会话开始(用户在此仓库发起求职相关对话时)

静默扫描 `applications/tracker.md`:
- "下一步日期"已到期且未完成的行 → 开场提醒(跟进草稿、催结果、面试准备)
- 状态为 applied 且超过 `config.yml` follow_up.default_days 无回音 →
  建议生成跟进草稿(草稿只给用户看,不代发)
- 状态为 applied 超过 21 天 + 2 次跟进无效 → 建议标记 ghosted

## 记录更新

- 状态词只能用 `applications/states.yml` 的 canonical 值(口语别名先映射)。
- 新增记录时补全表头所有列;JD 引用 `jds/` 文件,简历引用 `resumes/` 文件。
- 用户口头汇报的结果(如"挂了一面")→ 更新状态 + 在"备注/复盘"列记一句
  归因(为什么挂,能判断就记,不能判断就标"未知")。
- 面试细节 → 引导用户用 interview-prep skill 记录到 interviews/ 目录。

## 统计(用户要求时)

- **渠道漏斗**:按 `config.yml` channels 分组统计
  投递数 → 回复数 → 面试数 → offer 数,给出转化率。
  这是唯一必做的分析——社区实测内推转化可达海投 3~10 倍,
  没有这个数字就无法决定时间分配。
- 拒绝模式:对 rejected 的记录找共性(岗位族?级别?渠道?)列出,
  供用户调整策略。
- 投递节奏:近 4 周每周投递数,只陈述不评判(心理价值 > KPI)。
- 周报/跟进草稿等统计产物保存到 `applications/reports/YYYY-MM-DD-weekly.md`,
  跟进草稿必须在文件和会话中都标注"草稿,请确认后自行发送"。

## 边界

- 不代发任何跟进邮件/消息;草稿一律标记"草稿,请确认后自行发送"。
- 不修改历史记录的旧状态(追加备注可以,篡改历史不行)。
